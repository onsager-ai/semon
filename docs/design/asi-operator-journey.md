## Counting steps and the proposed budget

A command invocation, manual file creation/edit, protected transfer, external
infrastructure action, or explicit trust/permission approval each counts as an
operator action. Prompts inside one command still count. Automatically generated
files do not count as actions, but must be listed. Waiting for initial indexing
is elapsed time, not another action. Repeated failed attempts count in observed
usability tests. Installing Semon on each participating machine is recorded
separately, never silently treated as already done.

The owner's starting proposal is a **command budget**, not evidence that two
commands imply only two actions:

- A: install plus at most one startup command; no edited configuration.
- B: after installation, one command on each side; keys, certificates, credentials
  and grants for the authenticated owner generated by default; no edited files.
- Namespace, incarnation, epoch, credential kinds and issuer keys are internal
  details in normal use. Machine display names and data-sharing choices remain
  understandable user concepts.
- C: hand-edited policy/grant configuration is allowed for real multi-user sharing.

**Owner amendment (2026-11-11): push for fewer than five actions; single-owner
first is approved.** Proposed target: two commands, one protected paste into the
origin command's prompt, and one combined origin trust/source approval = **four
actions after installation**. Issuing a narrowly scoped invitation is the receiver
owner's deliberate authorization; removing a separate receiver identity review is
a real trust choice, listed below for approval, not a counting trick. Prompts
remain counted even when part of a command.

Endpoint reachability, firewall/DNS and unattended service installation are counted
separately if needed. A fresh remote server requiring these has not met the four-
action end-to-end target. Do not bury shell scripts, certificate tooling or a manual
policy file inside “install.” Routine browsing/query commands are use, not onboarding;
opening the authenticated Viewer and selecting the first evidence entry adds two
use actions. Initial indexing and publication waits must also be measured.

## B. One person, two or three machines — draft first

The receiver is the machine where the person wants to see combined analytics.
The origin is the machine that keeps native history and computes its own facts.
The receiver may also be an origin; its own local setup is scenario A. First
remote success means admitted analytics and an authorized online evidence read,
not merely a connected socket or successful credential import. Receiver search
remains unavailable under D8; local search stays available on each origin.

### Today's design: twelve setup tasks and no complete runnable path

Each row counts one task even where implementation will require several commands,
files or choices. Install is excluded. Only the local commands identified as
shipped can be run at the baseline. There is no honest end-to-end command count
for federation while publication, login and body integration are missing.

Thus the design exposes **at least twelve setup tasks versus two command
invocations proposed**, plus absent integration. It fails the proposed B budget;
calling it “twelve shipped commands” would be wrong. Three origins repeat the
origin-specific tasks; shared receiver custody should be provisioned once.

The three largest problems are:

1. **No single enrollment experience.** #634 exposes internal identities, two
   transfers and certificate tooling before the person can connect. Provisioning
   needs to generate those details while retaining explicit receiver trust.
2. **Connecting does not establish usable access.** Owner authentication,
   self-grants, source policy, cache key and audit setup are separate inputs.
   Generating key/files is cheap; choosing who may see which sources is real consent
   and must not be inferred from a successful transport connection.
3. **Lifecycle and recovery have no complete user path.** Producer startup,
   rotation, loss/revocation and audit exhaustion need named operations and clear
   outcomes. Neither deleting a state directory nor reissuing one token is a
   complete machine-removal or recovery procedure.

### Target setup, commands proposed for review only

The following command spellings are **UX proposals, not commands to run today**.
Retain `receive enroll` as the receiver's administrative entry point. A single
origin `connect` operation would import provisioning and explicitly enable the
local producer and outbound connection. This changes #634's provisioning design
and the store's explicit materializer lifecycle; PM approval is needed before code.

| Action | Proposed operation | Generated state / understanding |
| --- | --- | --- |
| B1 | Receiver: `semon receive enroll --machine laptop --listen 0.0.0.0:8735 --advertise https://desk.example:8735` | Local authenticated OS owner authorizes one invitation for the named machine. First run generates receiver identity/TLS custody, issuer key, separate cache key, owner principal, precise grants and audit directories. It starts receiver transport and a loopback-only owner Viewer in the foreground. Display a short-lived pairing string; subsequent enrollments use the already-owned service through a local administrative interface. No other OS user or remote machine gets an owner session. |
| B2 | Origin: `semon connect` | Starts the explicit local setup; prompts for the pairing string without echo. No secret in command arguments, history or URLs. |
| B3 | Copy the pairing string from the receiver terminal into the origin prompt through a trusted private channel | One transfer/paste action. The string carries the endpoint, receiver identity/trust pin and a high-entropy, single-use invitation secret. It is not a browser link or a short numeric code. Intermediate file saves, chat sends or extra copy operations add actions and exposure; they are not included in this four-action case. |
| B4 | Approve one combined trust/source summary inside `connect` | Explicitly trust this receiver as user-assertion issuer and approve the listed local source set plus typed name/path disclosure. Generate the client key on origin, bind it through invitation redemption, issue separate credentials and certificate, initialize the local producer, generate policy/registry from admitted sources, and connect. Receiver grants belong only to its OS-authenticated owner, not to the invitation bearer. |

This **T1 candidate** replaces #634's public bundle plus separate secret
transfer with a single-use provisioning exchange. The short-code T3 option below
is an alternative under evaluation; neither has owner approval. Invitation issuance delegates one enrollment, not arbitrary machine
administration or body authority. Use at least 128 bits of unpredictable secret,
a five-minute absolute expiry, one outstanding invitation per requested machine,
bounded attempts and atomic one-time redemption bound to the origin-generated
public key. A rejected/cancelled/expired attempt cannot activate grants or a claim.
Protect invitation state as credentials; never log the string or put it in URLs.
The plaintext is shown only at the explicit administrative terminal and accepted
only through a protected prompt. A retry after consumption does not enroll a new
key. User-facing status names the pending/connected machine without secrets.

The origin validates the receiver trust pin from the protected transfer, verifies
HTTPS hostname against the advertised endpoint and certificate, and proves
possession of its new key. A generated private trust root/certificate with the
correct endpoint identity can avoid an external certificate purchase; no system
trust store is modified. This pinned private-root provisioning is new to #634 and
the existing public-web-roots-only push client; implementation must update that
boundary explicitly. It is **not TOFU**: the trust pin comes from the independently
trusted transfer, not from the network peer being authenticated. Missing or wrong
pins fail closed; redirects are refused. The provisioning endpoint accepts only
this bounded invitation exchange and stays separate from body read routes.

Default selection is “all my currently discovered local sources,” with an
expandable list shown before approval. This is an explicit selection/owner policy
approval, not an assertion that all sources are safe. Existing floors and stricter
baselines win; unknown classification, missing scans, failed scans and unsupported
detectors do not become successful evidence. Remote bodies remain blocked unless
the actual governance requirements pass. New roots/sources discovered later remain
unapproved until another explicit local selection update; repeated sources under
an already selected policy still require a valid admitted contributor binding.
The generated registry derives complete contributor identities from the admitted
local snapshot and policy/scan outputs; it never fabricates a scan result or drops
a denied contributor to export a partial total. Hosted-model consent and replicas
stay off. The setup reports excluded or unavailable data without leaking it to an
unauthorized receiver user.

### Proposed first-owner policy profile

**P1 requires PM/owner approval before implementation.** A generated profile is
not permission to invent source classification or detector success. B4 proposes
one understandable choice covering: the named receiver and its authenticated owner
principal only; the listed currently discovered source cohort; typed receiver
analytics fields including plain names/paths and permitted coverage; and bounded
redacted body reads with encrypted cache (at most 15 minutes, 64 MiB/source and
256 MiB global, narrowed by any contributor). No Hub, other user, raw replica or
hosted-model evidence egress is included. Receiver-as-issuer trust is stated in
the same summary; decline keeps the source local.

For currently unclassified sources, the proposed profile asks the owner explicitly
to apply an `internal` floor to the displayed set. It never relabels an existing
`restricted` source or overrides a stricter baseline. Choosing “keep unclassified
sources local” is supported and may leave no exportable data. This floor decision
is part of B4's combined approval, not inferred from “all my local sources.” The
screen must show whether that set includes private/work material; the owner can
narrow it, and each additional selection action counts. No auto-approval of future
roots is implied.

The profile requests the current versioned detector/redactor requirements; it
cannot choose a weaker detector to obtain a green status. Fresh sources need an
actual origin-local scan over the admitted source generation and a recorded
supported detector/redactor result. #633 does not implement that scanner. Its
implementation, version/coverage semantics and policy binding are prerequisites
for this profile, routed by the PM to governance/origin owners. Failed, unsupported,
incomplete or stale scans refuse body egress. Existing analytics policy checks
still apply independently; no scanner is fabricated to allow publication.

The user sees “Share analytics (including names and paths), and approved redacted
evidence with my owner account on desk while this machine is online; apply internal
classification to these unclassified sources?” plus explicit excluded-source and
scan status details. Classification and redaction are fallible; this is not a
promise that secrets cannot escape. If the owner will not authorize P1 as a single
combined choice, split the policy decisions and raise the action count rather
than silently select a permissive default. Restricted sources remain local unless
a separate explicit named-reader/stream-through policy permits them.

### Trust options requiring PM/owner selection

| Option | Setup count on an already reachable receiver | What is gained and given up |
| --- | --- | --- |
| **T1: high-entropy one-use invitation (simpler implementation candidate)** | Four actions as above | Removes a separate receiver confirmation by authorizing possession of a narrowly scoped secret to bind one origin key. Someone stealing the invitation before redemption could occupy that enrollment and submit false origin facts. They gain neither existing body-read grants nor the owner's login, but can deny the intended pairing. Accept only with trusted private transfer, short expiry, atomic binding and visible completion/revoke. This changes #634's prior review of a known origin public identity. |
| T2: verify the origin identity on receiver before activation | Five actions: T1 plus receiver confirmation of a matching authenticated identity summary | Retains a separate receiver check; a stolen invitation alone cannot activate an enrollment. Misses the requested under-five target; offer if the owner rejects T1's delegation. |
| **T3: direct short-code PAKE (UX candidate; evaluate before selection)** | Four actions with address supplied in the origin command; see below | A reviewed password-authenticated key exchange replaces the long invitation/pin transfer. It resists offline guessing from captured exchange traffic; a code observed directly can still be used to race/impersonate a peer. Requires a reviewed bootstrap transport, maintained cryptographic implementation and aggregate guessing limits. No account identity is established by PAKE. |
| One-time browser link with a secret | Not proposed | A secret URL conflicts with the no-credential-in-URLs boundary. Pairing codes go into Semon's protected pairing input, never chat, arguments, browser history or logs. |
| Default-allow newly discovered or unscanned sources | Potentially fewer future prompts, **not proposed for delivery** | Gives up explicit source approval or fail-closed governance. It would require a separate security decision; selecting all current sources is not this option. |

D2, mTLS and dual audit are identical under T1/T2/T3. There is no proposed offline
grant, receiver-only authorization or machine-token-as-user shortcut. Four actions
is a design target conditional on the chosen provisioning option, P1 approval and
complete implementation, not an accepted security tradeoff.

### T3 option: direct short-code pairing

The PM supplied a T3 Code UX observation on 2026-11-11: account sign-in, an app
pairing card, code entry on the other machine, selectable access, visible endpoint
reachability and links observed to expire after roughly four weeks. This is
exposed-surface evidence, **not source/protocol evidence**. It does not establish
that T3 uses PAKE or that its observed lifetime should become Semon policy. Semon
borrows the interaction pattern without its account system, service or state.

PAKE means a password-authenticated key exchange: a short shared code establishes
a cryptographic session without exposing that code to offline guessing from a
captured protocol transcript. Candidate families include SPAKE2 or CPace; no exact
construction/library is selected here. [RFC 9382](https://www.rfc-editor.org/rfc/rfc9382.html)
(SPAKE2, Informational, especially sections 3.1–3.3) describes transcript identities
and confirmation MACs. [RFC 8125](https://www.rfc-editor.org/rfc/rfc8125.html)
(sections 1 and 4) describes PAKE requirements and interactive-guessing/denial-of-
service tradeoffs. These references are not implementation approval.

Proposed replacement for B1–B4, still **four counted actions**:

1. Receiver owner runs `semon receive enroll --machine laptop --listen
   0.0.0.0:8735 --advertise https://desk.example:8735`. Semon shows a short-lived
   random code in its local authenticated pairing surface and waits for one peer.
2. Origin owner runs `semon connect --to https://desk.example:8735`. Address is a
   nonsecret command input. Choosing or discovering it is not authenticated pairing;
   any extra lookup, picker or address-entry step is recorded in a usability run.
3. They enter the code directly in the origin's non-echoing Semon prompt, never
   through chat. Both peers automatically complete cryptographic key confirmation.
4. They approve the origin's authenticated receiver/issuer, read-only sharing and
   P1 source summary. Only then activate scoped enrollment and source publication.

Code submission and permission approval remain separate counted actions, even if
one UI button ultimately submits both. A separate human check of the origin on
the receiver adds a fifth action. The receiver's initial administrative command
otherwise delegates one binding to possession of the code, with the same
identity-selection limitation as T1. Cryptographic mutual confirmation proves
shared key possession; it is not a human's independent verification of a machine
or a signed-in account. Peer-provided names are labels, not identity evidence.

Semon's only access choices are read-only sharing of analytics and approved
on-demand evidence, or a narrower analytics-only scope. Do not copy T3's approval,
execution or full-access controls. The receiver's authenticated local OS owner
still supplies its principal and owner browser session; PAKE creates no user login
and does not make remote headless-owner authentication free. The code chooses no
source classification and cannot bypass source policy.

**Bootstrap must be specified before this option is selected for implementation.**
With an existing trusted HTTPS endpoint, normal TLS identity validation precedes
PAKE. With a LAN/private certificate, a code alone does not supply its trusted
root. A distinct bounded bootstrap protocol must authenticate and bind the endpoint,
receiver TLS identity/pin, origin-generated public key, roles, fresh session,
version and intended enrollment scope through the PAKE-confirmed channel before
persistent trust or credentials activate. That might require a dedicated bootstrap
transport; it is not a general “accept invalid certificates” switch. No application
body, credential, grant or policy enters an unauthenticated channel. No silent
TOFU or request-installed issuer pin on the body routes. Following provisioning,
normal HTTPS hostname/pin checks and body mTLS remain mandatory. LAN/Tailscale
reachability, where already available, is a transport convenience, not proof of
Semon identity; neither is required infrastructure.

Use an established maintained implementation and independent protocol review;
these have **not been assessed yet**. Require explicit confirmation from both
peers, bounded pending state, a minutes-long absolute invitation lifetime,
atomic single-use activation and cancellation that leaves no active grant.
Choose code entropy/length and attempt limits together in that review. Limits
must apply per invitation/session and receiver-wide across addresses, connections,
retries and repeated invitation issuance; per-IP limits alone are insufficient.
Lockout can deny legitimate pairing, so report the recovery action without an
unbounded automatic retry/reissue loop. Expiry/failed confirmation cannot activate
a partial enrollment. No code or key in logs, URLs, assertions or error text.

**Owner option: code exposure and confirmation.** Recommend direct entry from a
trusted receiver display into the trusted origin, and reject chat-based pairing
as the documented flow. A network observer without the code cannot perform offline
guessing against a sound PAKE transcript; an attacker who sees the actual code
can race or impersonate a participant. PAKE does not make an untrusted messenger,
screenshot or remote screen safe. If untrusted code delivery is required, either
accept that exposure explicitly as a security tradeoff, or add independent identity
verification via a trusted channel and count its extra actions. Endpoint compromise
or remote control of either device cannot be repaired by PAKE.

Recommendation for PM/owner: evaluate T3's four-action short-code option with a
bounded protocol/library review; retain T1 as the simpler alternative. Do not
claim a three-action result or select an insecure bootstrap to meet a count.

### Expiry and re-pairing as the normal renewal flow

**E1 is a separate owner choice, not implied by the pairing selection.** One option
is a finite enrollment authorization lifetime followed by the same pairing flow,
with a clear expiry warning and no new publication/body reads after expiry. This
reduces routine credential instructions to “re-pair this machine,” but each renewal
costs the pairing actions and offline machines may lose access until the owner
returns. The observed T3 four-week lifetime is an example only; choose Semon's
lifetime deliberately. The alternative is automatic transport credential renewal
under still-valid explicitly enrolled trust, with manual re-pair after trust loss
or compromise; it has fewer recurring actions but longer standing authorization.
Both need independent revocation at the next decision/release, not expiry-only
access removal. Revocation must also stop active delivery within declared bounds.

Keep invitation expiry, enrollment lifetime, client-certificate/bearer validity,
owner browser session, short read-assertion validity and D3's cache TTL distinct.
Re-pair may replace origin transport credentials/certificate through one guided
operation; old generations must become unusable at the documented cutover. It
must preserve native namespace/handle continuity where proven, prior facts, source
restrictions and audits. A revoked enrollment is never resurrected: explicit new
enrollment uses a new ID and reconciles current authority, not a stale bundle.
Lost keys or changed origin incarnation cannot silently transfer publisher claims.

Re-pair does not by itself rotate the receiver's assertion-issuer key, server/root
identity or cache master key. Those serve different custody and trust boundaries.
If re-pair is chosen to distribute new issuer/root pins, the ceremony must explicitly
bind that new trust, keep at most two issuer keys during an approved bounded overlap,
and account for each origin. Compromised trust needs a fresh independently trusted
ceremony; routine renewal authenticated only by the compromised key is insufficient.
Cache key rotation remains a receiver-local explicit invalidation operation and
never deletes facts/audits. Show advanced identity maintenance only when needed,
but retain its operational contract beneath a simple normal renewal experience.

### Network and service costs outside pairing

The four-action case assumes two installed binaries, a known reachable receiver
address and local access to its owner session. A LAN receiver may use an address
already routable from the origin; B1 supplies it and generates a matching pinned
certificate. A remote receiver may require DNS, firewall changes or a reachable
host before B1: record each action, provider login and monetary choice. Semon does
not acquire infrastructure or change the firewall silently. Neither relay nor T3
is required or offered as fallback.

B1/B2 keep Semon's receiver and origin producer/channel running in their foreground
processes. Closing those processes stops new synchronization/body reads; analytics
already admitted remains. Reboots require restarting them until an explicit
service-install workflow exists. Proposed `semon service install` on each side is
**two additional command actions**, plus any privilege approvals; do not claim four
actions for unattended operation. No service is silently installed by enrollment.
A headless receiver requiring remote browser login adds an authentication workflow;
that is not the four-action local-owner baseline. Delivery must state this limit
rather than expose the loopback Viewer or reuse a machine invitation for login.

**Host custody is also a prerequisite, not a free setup step.** The four-action
case is an already-supported Unix host with owner isolation, trusted private state
storage, no unencrypted swap and no backup/snapshot policy that captures body-cache
files or their separate secret custody together. The command can create/check
private directories/files, disable core dumps for its own body-serving process and
report the selected paths. It cannot assume system crash collectors, swap or an
external backup agent are safe. Check supported observable host settings and require
reviewable operator evidence for external backup exclusions; an extra attestation
or host change adds an action. Unknown/failed custody checks leave body serving
disabled, with analytics-only partial setup clearly reported. Selecting stream-
through avoids body disk cache but does not remove plaintext memory/core/swap risks
and is not a silent fallback. Required host administration may make a new machine
exceed four actions; record it alongside networking and services. The proposed
budget is conditional, not a universal clean-host deployment promise.

Successful completion reports: “laptop connected; analytics received; evidence
available while laptop is online,” with admitted freshness and explicit exclusions.
An unsupported source/detector may yield analytics but unavailable evidence; that
is a partial result, not full B success. Background scheduling here means Semon's
own local collection/publication, never harness execution or remote control.
Unattended OS service installation is not silently included.

## A. One machine: install, analytics, search and view

### Current runnable path and packaging gap

There is no supported one-command ASI installer in the baseline. The Linux workflow
artifact is obtainable with the command documented in
[release-binary.yml](../../.github/workflows/release-binary.yml), but that workflow
builds without `asi-query`. It cannot complete this journey. A query-enabled binary
must first be built in CI using `cargo build --locked --release -p semon-cli --bin
semon --features asi-query`, then installed into the user's PATH with executable
permissions. This is a packaging prerequisite, not a request to run a local build.
An install recipe must name a verified artifact/revision and supported platform;
this proposal does not invent an existing release URL.

With that binary installed, the current commands are:

```sh
semon analytics materialize
semon query sql 'SELECT COUNT(*) AS sessions FROM fact_session'
semon query search 'timeout'
semon query view FULL_ASI_UID
semon sessions --serve
```

`FULL_ASI_UID` is replaced with a `body_uid` returned by search, not a native
session filename. The first command refreshes the full local Catalog and drains
analytics through its captured endpoint. It is one-shot; use
`semon analytics materialize --watch` for ongoing publication in a separate process.
Opening Viewer or MCP does not start that writer. `semon query schema` supplies
table/column reference without requiring the user to read storage internals.

| Step | Files touched | What the person must know |
| --- | --- | --- |
| Install query-enabled binary | Chosen executable destination | Ordinary artifact omits the feature; this must be fixed in packaging |
| Materialize | `$XDG_STATE_HOME/semon/` or `~/.local/state/semon/`: `sessions-index.sqlite3` and SQLite sidecars, `archive/`, `analytics-namespace`, `analytics-store/` and lock | Local only; initial full history can take time; unsupported existing state is preserved and refused |
| SQL/search/view | Existing analytics/index snapshots and bounded worker scratch state; no author-state edits | SQL reads body-free facts; search/view read local private text; copy an exact returned UID |
| Start Viewer and open its printed local launch URL | Local Catalog/index state, per-run authenticated browser session | Loopback authenticated read-only browser; local launch bootstrap is distinct from ASI API URLs, which never accept credentials |

Current onboarding needs **two startup commands** (materialize and serve), then
opening the Viewer. CLI demonstrations add three use commands. Therefore A meets
“one explicit materialization” but **does not meet install plus one startup command
for an integrated analytics/search/browser experience**, and ordinary packaging
cannot deliver ASI query at all. The `/api/asi/*` routes are delivered local APIs,
not evidence of completed analytics/search controls in the UI.

### Proposed A target

Proposed, unimplemented: `semon start` explicitly initializes local collection and
analytics, keeps the writer running and opens the authenticated loopback Viewer.
It is one startup command after a query-enabled install. The word “start” means
Semon's own read-only collection/UI, never starting or controlling a harness.
No remote export or enrollment is enabled. Show initial preparation, admitted
freshness and source availability; do not show a plausible empty dashboard while
work is pending. Stop leaves all durable history intact. If automatic browser
opening is unavailable, opening the printed local launch address is one additional
use action, recorded separately. Unattended service setup remains additional.

This needs an explicit producer-lifecycle amendment to the store contract, where
`analytics materialize` is currently the only enablement surface. Preserve that
low-level batch command for scripts; no implicit rebuild on a read, no fallback
reset and no change to the source integrity boundaries. Exact UI work remains in
Storybook under the existing Viewer owners.

### Authoring, backup and exceptional recovery

These are optional operations, not prerequisites for first analytics. Current
commands (examples use a new destination and existing trusted state):

```sh
semon asi add lane --id investigation --values -
semon asi backup /private/backups/durable.sqlite3
semon analytics export /private/backups/analytics
semon analytics reset --confirm EXACT_NAMESPACE --verified-export /private/backups/analytics
```

The first command reads a JSON object from stdin, for example
`{"title":"Investigate query latency"}`; the user ends stdin normally. No hand-edited
file is required. It writes author-owned `asi-durable.sqlite3` and sidecars under
the author lock; it is not a remote write API. The backup command requires its
parent directory to exist and refuses an existing destination. Analytics export
copies the current local analytics snapshot and receipt; it is **not** a backup
of native archives, all private enrollment state, or durable free text. Both
backups are sensitive operator custody; use a private destination. Materialization
is still needed to reflect durable categorical changes in analytics.

Reset is exceptional destructive maintenance, never part of install, onboarding,
format upgrade, machine removal or a “fix it” button. Its exact namespace check and
verified-export requirement protect real non-rebuildable facts. `--without-export`
is an explicit loss waiver; `--new-namespace` changes identities and retires the
private egress-handle mapping. Preserve both guards and explain their consequences.
A proposed guided recovery command may discover/display the exact identity and
invoke the existing guarded operation after confirmation; it must not silently
select the waiver, forge an export or assume imported history can be rebuilt.
Unsupported formats remain intact; the matching older binary may export its own
custody under the current documented recovery procedure, without a new-version
migration/import adapter. Native sources, archives and durable author state are
not reset by analytics maintenance.

### Backup and recovery beyond the two shipped export commands

No complete federation backup/restore CLI ships today. Before relying on B for
custody, the operator needs a documented consistent snapshot procedure and a
restore verifier; both are follow-up design/implementation, not `cp` of a running
SQLite database. A proposed `semon backup --destination /private/backups/snapshot`
would coordinate the relevant local writers and current-format backup APIs, show
its coverage, and preserve each custody class separately. Destination creation,
secret-vault provisioning, backup execution and any restore confirmations are
maintenance actions outside onboarding, counted when exercised.

| Custody | What to preserve separately | Recovery rule |
| --- | --- | --- |
| Native evidence | Native originals where owned, immutable `archive/` chains/manifests and exact dependency/custody records | Restore verified admitted sources through existing native readers; never infer completeness from analytics alone. Absent sources mean frozen facts/unavailable bodies. |
| Local identity and evidence mappings | `analytics-namespace` and `analytics-egress-handles.sqlite` as a consistent private namespace-bound checkpoint; index custody/provenance as applicable | Preserve together for stable exported handles. Analytics export excludes handles. Missing mapping must be reported as lost continuity, not silently advertised as the same evidence links. No namespace transfer to a replacement machine without explicit authority review. |
| Analytics and author state | Verified analytics custody export plus separate `asi backup` output and imported receiver heads in their owning store | Current-format validation first; do not reset frozen/imported facts or pretend local export covers all receiver namespaces. Durable free text remains author-owned. |
| Enrollment/trust/secret state | Integrity-protected registry, revocation history, pins and policy; private keys/credentials only in an explicit separately protected secret backup | Restoring a stale registry must not revive revoked authority. Offline backup alone cannot establish current revocation state. Lost/compromised or unverifiable keys require fresh enrollment/rotation, not automatic recovery from an old invitation. |
| Audit | Separate sensitive origin and receiver journals, locks/format and custody checkpoint under an explicit preservation procedure | Preserve attempts/receipts, validate before reuse; corruption/full state refuses. Never merge, repair or prune silently. An explicit fresh journal retains the old journal as history. |
| Temporary body cache | Exclude ciphertext, staged bodies and cache keys from ordinary history backups | Recreate empty under a new generated cache key; all future reads still need online origin authorization and both audits. Cache is not a recovery source. |

A lost-machine `revoke` is containment. Recovery first inventories surviving
custody, verifies current authority independently of stale backup state, and either
restores that same legitimate origin under an explicit rebinding workflow or
creates a new enrollment. Neither workflow is implemented by this docs proposal.
Permanent source loss and namespace authority transfer remain explicit decisions
under D1/D6; no recovery command silently grants replica/offline read authority.

## C. Shared receiver: deferred product surface, retained enforcement

**Owner approved single-owner first on 2026-11-11.** Shared-user login, groups,
invitation/admin screens and grants UI are deferred. The single owner still has a
stable authenticated principal, exact machine/namespace grants, origin source
policy and both read audits. No wildcard “local means authorized” bypass is
allowed. Remote bodies still require online authorization, even on cache hits.

C cannot be run end-to-end today. There is no CLI for creating/login of shared
users or managing receiver ACLs. The following is an integration journey, not a
claim that editing `grants.json` activates safe shared access:

| Step | Operator action / future surface | Files and concepts | Can defer? |
| --- | --- | --- | --- |
| C1 | Provision HTTPS and an authenticated user identity provider/session boundary | User identity and stable opaque audit ID mapping, distinct from machine credentials; remote Viewer exposure needs its own authorization contract | Yes; keep first delivery loopback owner access |
| C2 | Enroll each origin using B; source owner selects permitted readers locally | Enrollment and generated source policy; receiver-as-issuer trust is explicit, external issuer is an advanced option | Shared-reader selection UI yes; origin policy enforcement no |
| C3 | Admin writes/validates scoped grants, later uses a grants command/UI | Dedicated owned 0700 ACL directory, 0600 `grants.json`; analytics and body_read are separate | Shared grants UI yes; fail-closed ACL checks no |
| C4 | Each user signs in and sees only admitted machines/analytics | Per-request principal filtering before discovery/SQL and exact body authorization; uniform cross-user denials | Shared login/UI yes; first-owner isolation no |
| C5 | View evidence or explicitly inspect audit status | Separate origin/receiver `attempts.jsonl` and locks; attempts durable before bytes, bounded receipts | Audit browsing UI yes; both journals, capacity/refusal and private custody no |
| C6 | Revoke a user/group or change permitted sources | Read-at-decision grants and local origin policy; cancel/recheck active delivery | Shared admin UI yes; revocation checks no |

Existing ACL JSON input, **for a future authenticated integration only**:

```json
{"format":1,"grants":[{"principal":"alice","machine":"laptop","namespace":"origin-example","permissions":["analytics","body_read"]}]}
```

Here `alice` must be the caller-authenticated principal and `origin-example` the
actual enrolled namespace, not values invented by a browser request. Invalid,
missing, insecure or unsupported ACL files deny. Source policy can narrow the
receiver grant. Editing this file alone supplies no authentication, origin consent
or cache authority. Hand editing may remain an advanced C escape hatch, with
validation and atomic publication; it is never the A/B quickstart.

## Generated files and normal-use concepts

Local paths below that are not already specified are **proposed layout roles**, not
new accepted filenames. On-disk names belong to #634 implementation after review.

| Machine | Existing / generated custody | Normal explanation |
| --- | --- | --- |
| Every origin | Existing state root: index/sidecars, `archive/`, `analytics-namespace`, `analytics-store/`, optional `asi-durable.sqlite3`; `analytics-egress-handles.sqlite` | “Your local history and analytics.” Keep source identity stable; never delete to reconnect. |
| Origin enrollment | Proposed private `connections/` config and separately protected credentials/client keys, generated source registry/policy; separate origin audit directory | “Connected to desk, sharing the sources you approved.” Show destination and choices; internal epochs/incarnations stay diagnostic. |
| Receiver | Proposed private enrollment/credential-hash registry, receiver TLS/issuer keys, separate cache master key, owner principal and ACL directory | “Only your signed-in owner can read these machines.” No key lives in cache or exported bundle. |
| Receiver data | Imported immutable analytics heads; separate encrypted cache; separate audit directory with `audit.lock` / `attempts.jsonl` | “Analytics stays; evidence needs the origin online.” Cache expiry never removes facts or audit. |

Generated private files use owned directories and checked modes/links, atomic
updates and no symlink traversal as required by their libraries. Do not invent a
universal config file that mixes secrets, bodies, audit and policy custody.
Normal status reports machine, destination, selected sources, last admitted
publication and evidence availability. Advanced diagnostics may expose opaque
bindings without secrets or body text. Example refusal copy is specific and
remedial: “Laptop is offline. Analytics is still available; new evidence reads
need laptop online.” “Source policy blocks this read” must not disclose a source's
existence to a user without discovery permission. Audit-full errors name a local
administrative action; unsupported-format errors preserve data and do not offer
automatic reset. Machine-readable error codes stay stable within the current
contract; human wording does not smuggle secrets into errors.
